# Migrating to 0.9.0 — typed Swift maps, record writer changes

0.9.0 is a breaking release. 0.8.9 was never published; its changes are part
of 0.9.0.

1. Set `nitro`, `nitro_annotations` and `nitro_generator` to `^0.9.0`. An app
   can hold one `nitro` version, so every Nitro plugin it uses must move
   together.
2. Regenerate and relink: `nitrogen generate && nitrogen link`.
3. Fix the hand-written code below. Kotlin implementations need no change.

## Swift: maps are typed

A protocol method took and returned `Any` for every map. It now uses the
dictionary type of the spec.

```swift
// 0.8.x
public func echoIntMap(value: Any) -> Any { value }

// 0.9.0
public func echoIntMap(value: [String: Int64]) -> [String: Int64] { value }
```

| Dart | Swift |
|---|---|
| `Map<String, int>` | `[String: Int64]` |
| `Map<String, int?>` | `[String: Int64?]` |
| `Map<String, Config>` (record, variant, enum, flat struct) | `[String: Config]` |
| `NitroAnyMap` | `[String: Any]` |
| a nullable map | the same type with `?` |

The compiler names every method that needs the change.

## Swift: `NitroRecordWriter`

`toNative()` empties the writer, and `bytes` is a read-only copy. Code that
called `toNative()` and then read the writer again must read first.

## C++: `NitroRecordWriter::_buf` is gone

The writer is not copyable and its buffer is private. Read the payload with
`toBuffer()`.

```cpp
// 0.8.x
blobs.push_back(std::move(w._buf));

// 0.9.0
NitroCppBuffer b = w.toBuffer();
blobs.emplace_back(b.data, b.data + b.size);
```

## A map property on Kotlin or Swift is refused

`Map` and `NitroAnyMap` properties generated native code that did not build.
The validator now reports `INVALID_PROPERTY_TYPE`; use a getter method.

## Web needs no plugin entry

`nitrogen init` used to add a web plugin class. It did nothing: the generated
platform shim picks the web bridge with a conditional import. It also made the
plugin depend on `flutter_web_plugins`, which SDKs without a web target
(DartNative) do not have, so the plugin could not be resolved there.

New plugins no longer get it. In an existing plugin:

1. Delete `lib/<plugin>_web.dart`.
2. Remove `flutter_web_plugins` from `dependencies`.
3. Remove the `web:` entry under `flutter: plugin: platforms:`. Keep
   `assets: - assets/web/`.
4. Declare every platform, web included, at the top level so pub.dev still
   lists them:

   ```yaml
   platforms:
     android:
     ios:
     web:
   ```

`nitrogen doctor` warns while the old layout is in place. A Flutter web app
needs no other change.

## Running an existing Kotlin or Swift plugin in DartNative

New plugins from `nitrogen init` need nothing. For a plugin scaffolded before
0.9.0:

**Android.** DartNative gives plugin projects no Kotlin support, and its
embedding has `FlutterPlugin` but no `plugins.activity` package.

1. In `android/build.gradle`, after the `plugins { }` block:

   ```groovy
   if (extensions.findByName("kotlin") == null) {
       pluginManager.apply("org.jetbrains.kotlin.android")
   }
   ```

   Keep it as `pluginManager.apply`: Flutter reads the file for an
   `apply plugin:` line and then warns that the plugin applies Kotlin itself.
2. In the plugin class, remove `ActivityAware` and its four methods. To keep
   the Activity, register `Application.ActivityLifecycleCallbacks` in
   `onAttachedToEngine` and forward to `<Class>JniBridge.onActivityAttached`
   / `onActivityDetached` (a new scaffold shows the code).

**iOS.** DartNative never calls the plugin's `register(with:)`, so nothing
registered the Swift implementation and every call returned a default value.
The generated registry now asks a provider class on first use. Adopt it:

```swift
public class SwiftMyPlugin: NSObject, FlutterPlugin, MyPluginImplementationProvider {
    public static func register(with registrar: FlutterPluginRegistrar) {
        registerMyPluginImplementation()
    }

    public static func registerMyPluginImplementation() {
        MyPluginRegistry.register(MyPluginImpl())
    }
}
```

## Dart-only projects on macOS

`NitroRuntime.loadLib` used to look only inside the running process on macOS,
which is right for a Flutter app and never works for `dart run`. It now opens
`lib<name>.dylib` from the loader's search path when the process does not
contain the bridge, as it already did on Linux and Windows.

## What you can remove

These workarounds are no longer needed (see [LIMITATIONS.md](../LIMITATIONS.md)):

* one map parameter per method, and a map return only next to a map parameter;
* `@zeroCopy` or a wrapper record to return typed data, nullable or not;
* a record in place of a flat `@HybridStruct` as a map value or a callback
  return.

## Tools that import the generator's `src/`

The extractor, the validator and the C bridge, web and Swift function
generators were split into one file per concern. Generated output is the
same. [doc/generator_architecture.md](../doc/generator_architecture.md) lists
where each piece lives.
