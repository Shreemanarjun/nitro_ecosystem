# Record codec: cost per type, per language

What each `@HybridRecord` field kind costs to encode and decode in the generated
Dart, C++, Kotlin and Swift codecs, what was changed, and what is left.

Method: one record per type family, generated by the real generator; each codec
timed on the same wire bytes; every native codec also checked to re-encode
Dart's bytes exactly. Dart is AOT, C++ `-O2`, Swift `-O -wmo`, all on macOS
arm64. Kotlin is on the Android emulator (ART, arm64, API 34, `app_process`), so
its absolute numbers are a JIT without an AOT profile. 1 024 elements unless
noted; times are per call, before → after.

## Dart and C++

| Field | Dart encode | Dart decode | C++ encode | C++ decode |
|---|---|---|---|---|
| `{int, double, bool, String}` | 75 → 73 ns | 65 → 52 ns | 40 ns | 18 ns |
| `String`, 1 KiB ASCII | **1 050 → 726 ns** | **536 → 178 ns** | 90 → 84 ns | 52 ns |
| `String`, 1 KiB of 2-byte UTF-8 | 1 712 ns | 1 258 ns | 90 ns | 54 ns |
| `List<int>` | **3 559 → 1 339 ns** | **2 800 → 1 620 ns** | **1 260 → 236 ns** | **2 097 → 239 ns** |
| `List<double>` | **3 727 → 1 292 ns** | **3 457 → 2 690 ns** | **1 188 → 203 ns** | **2 094 → 263 ns** |
| `List<bool>` | **3 074 → 1 121 ns** | **2 462 → 1 315 ns** | **1 490 → 498 ns** | 2 261 ns |
| `List<String>` (16 chars) | 19.8 µs | **23.6 → 14.8 µs** | 5.8 µs | 4.8 µs |
| `List<Record{double, double}>` | 8.7 µs | 7.1 µs | 4.5 µs | 2.9 µs |
| `Uint8List`, 1 KiB | 84 ns | 78 ns | 90 → 85 ns | 64 → 59 ns |
| `Int32List` | 191 ns | 248 ns | 138 ns | 129 → 93 ns |
| `Float64List` | 347 ns | 398 ns | 232 ns | **249 → 168 ns** |
| variant, one `double` | 51 ns | 31 ns | 32 ns | 17 ns |
| variant, `String` (64) + `int` | 104 ns | 52 ns | 37 ns | 50 ns |

Changes:

- **Dart, string decode.** ASCII is checked eight bytes at a time and built with
  `String.fromCharCodes`; anything else goes to the UTF-8 decoder.
- **Dart, string encode.** From 16 characters up, eight code units are packed
  into one store (0.7 ns per character instead of 1.0); the first non-ASCII word
  ends the attempt, so other text pays nothing extra.
- **Variants** were only timed (new rows above, measured after the changes).
  They sit at the per-call floor: a scalar record is 73 / 52 ns.
- **Dart, primitive lists.** `writeIntList` / `writeDoubleList` / `writeBoolList`
  do one capacity check for the list instead of one per item. `readIntList` /
  `readDoubleList` / `readBoolList` build the list from a closure that indexes
  the payload through locals; the generated `List.generate(n, (_) => r.readInt())`
  stored the reader's position once per item, which was 1.4–1.9× slower.
- **C++, `List<int>` and `List<double>`.** The wire form is the vector's own
  storage, so each direction is one `memcpy`.
- **C++, `List<bool>` encode.** Unpacked 256 items at a time, one append per
  chunk instead of one per item.
- **C++, typed data.** `assign` from the payload instead of `resize` (a zero
  fill) and then a copy.

## Kotlin (ART)

| Field | Encode | Decode |
|---|---|---|
| `{int, double, bool, String}` | **525 → 150–173 ns** | **239 → 121 ns** |
| `{int?, double?, String?, bool?}` | **632 → 171–206 ns** | **266 → 135 ns** |
| `List<int>` | **63.6 → 3.1 µs** | **22.9 → 2.5 µs** |
| `List<double>` | **64.3 → 3.0 µs** | **24.3 → 2.6 µs** |
| `List<bool>` | **9.9 → 4.2 µs** | **10.1 → 1.2 µs** |
| `List<String>` (16 chars) | **183 → 43 µs** | **137 → 58 µs** |
| `List<Record{double, double}>` | **147 → 29.6 µs** | **46.5 → 22 µs** |
| `Uint8List`, 1 KiB | **862 → 420 ns** | 276 ns |
| `Int32List` | **50.2 → 3.2 µs** | **3.5 → 1.8 µs** |
| `Float64List` | **57.5 → 6.1 µs** | **13.3 → 3.1 µs** |

On the desktop JVM the same changes take `List<int>` encode from 10.9 to 1.3 µs,
`Int32List` from 10.7 to 0.35 µs and a list of records from 21.4 to 5.7 µs.

Changes:

- `encode()` writes into `NitroRecordOut`, a `ByteArrayOutputStream` subclass
  that puts little-endian values straight into its own array. A plain stream
  cost a lock, a scratch buffer and three calls per value. It is still a
  `ByteArrayOutputStream`, so the `writeFieldsTo(out, buf)` contract the struct,
  variant and function emitters call is unchanged, and a plain stream still
  works. Each generated Kotlin file has its own package, so one such class per
  file cannot collide.
- Typed arrays go through a typed view of the buffer in one bulk `put`/`get`.
- `List<int>` / `List<double>` / `List<bool>` are read into a primitive array
  and exposed with `asList()`, so nothing is boxed until an element is used.
- Strings are decoded where they lie in the buffer's array instead of through a
  copied `ByteArray`, and ASCII goes through the Latin-1 decoder, which on ART is
  1.1–1.6× faster than the UTF-8 one over the same bytes (a 16-character
  string: 178 → 58 ns; 1 KiB: 2.2 → 1.7 µs). The variant writer uses the same
  direct-write stream as records.
- An ASCII string of up to 64 characters is written char by char into the
  stream's array (16 characters: 103 → 23 ns on ART). Past 64 characters the
  platform encoder is faster, so longer strings and any other text still use it.
- `List<int>` / `List<double>` are written with one capacity check and a local
  write index, by `get(k)` when the list has O(1) access: an `ArrayList<Long>`
  goes from 6.8 to 3.1 ns per item on ART. A list the decoder produced is a
  view of the array it was read into (`NitroLongList` / `NitroDoubleList`), and
  is written back with one bulk put instead of boxing every item (the table's
  figure: 10.7 → 3.1 µs).
- `List<bool>` is read with one bulk `get` instead of one per item.
- Records decode through `NitroRecordIn`, a cursor over the byte array, instead
  of `ByteBuffer` accessors, which on ART cost about four times as much per
  value. `decodeFrom(buf: ByteBuffer)` is still there for the struct, variant
  and function emitters and runs the same decoder; a struct or another
  module's record inside a record is handed a `ByteBuffer` at the cursor.
- The variant reader decodes strings where they lie, ASCII as Latin-1, as the
  record cursor does (it copied each one into a `ByteArray` first).
- `encode()` reserves the length prefix up front instead of concatenating it
  (one copy of the payload less), and the per-thread stream is dropped after a
  record over 4 MiB instead of being held for the life of the thread.

## Swift

| Field | Encode | Decode |
|---|---|---|
| `{int, double, bool, String}` | **314 → 82 ns** | 110 → 87 ns |
| `{int?, double?, String?, bool?}` | **364 → 87 ns** | 114 → 87 ns |
| `String`, 1 KiB ASCII | **259 → 125 ns** | 111 → 81 ns |
| `List<int>` | **6 878 → 220 ns** | **2 089 → 201 ns** |
| `List<double>` | **6 935 → 222 ns** | **2 105 → 204 ns** |
| `List<bool>` | **2 571 → 115 ns** | **2 094 → 90 ns** |
| `List<String>` (16 chars) | **68.3 → 11.5 µs** | **56.0 → 40.7 µs** |
| `List<Record{double, double}>` | **11.3 → 5.1 µs** | 2.1 µs |
| `Uint8List`, 1 KiB | **314 → 126 ns** | 108 ns |
| `Int32List` | **603 → 171 ns** | **266 → 147 ns** |
| `Float64List` | **825 → 216 ns** | **434 → 220 ns** |

Changes:

- The writer holds one `malloc`'d `[4B length][payload]` block and `toNative()`
  hands it to Dart, as the C++ writer does. It was a `[UInt8]` copied into a
  fresh block for every record. This is most of the gain on small records.
- `[Int64]` / `[Double]` and typed arrays are copied from, and into, the array's
  storage in one pass (they went through `Data` and `Array(...)`).
- `[Bool]` is written from the array's storage (a `Bool` is the byte 0 or 1)
  and read by comparing each byte in one loop the compiler vectorises.
- An indexed list is written by one writer with a back-filled offset table; it
  was a writer and a byte array per item.
- Strings are decoded with the standard library's decoder instead of
  Foundation's.

`toNative()` now gives the writer's block away, so it empties the writer; `bytes`
is a read-only copy of the payload.

## Bugs this turned up

All four existed in 0.8.8 and are fixed here.

- **Kotlin did not compile** a record with a `String?`, a nullable typed list or
  a nullable `List<…>` field (`}()` after `else` is a block, not a call; the list
  was declared non-null).
- **A leading U+FEFF was dropped** from string fields decoded by Dart and by
  Swift, and from map keys and values on both. Foundation's and dart:convert's
  decoders treat it as a stream signature.
- **`@zeroCopy` typed-data returns** dangled when returned from `Isolate.run`
  (see below).
- **The C++ reader's bounds check could wrap**: `_offset + n > _size` passes for
  a length near `SIZE_MAX`. It is now `n > _size - _offset`, and list lengths are
  rejected when negative.

## Typed-data fields are lent, not copied

A typed-list field (`Uint8List`, `Float32List`, …) of a record Dart owns (a
method return, a `@nitroNativeAsync` result, a stream item) is a view of the
record's native buffer instead of a copy: 1 MiB `Uint8List` 192 → 51 µs, peak
memory 4× → 2× (AOT, macOS). The wire format is unchanged.

- Fields under `RecordReader.lendMinBytes` (8 KiB) are copied, which is faster
  below about 4 KiB. One field per record is lent; a second large one is copied.
  Set `RecordReader.lendMinBytes = 1 << 62` to switch lending off.
- The buffer is freed when the list is collected, through a per-module export
  (`<lib>_nitro_adopt`, a finalizable handle). `asTypedList(finalizer:)` is not
  used: dart:ffi frees such memory when the creating isolate exits, so a list
  returned from `Isolate.run` / `compute` would point at freed memory.
- Hand-written C++: `NitroRecordWriter::_buf` is gone and the writer is not
  copyable; read the payload with `toBuffer()`. The struct sits in an inline
  namespace so plugins generated before and after link into one binary.

`tool/verify_cpp_bridge_compiles.dart` also could not fail CI: it returned its
result from `main`, which Dart ignores.

## Gates

- `tool/verify_record_wire.dart` — every field kind and every nullable form;
  C++, Swift and Kotlin must re-encode Dart's bytes exactly. Run against the
  0.8.8 generator it fails on Kotlin (does not compile) and on Swift (the BOM).
- `tool/verify_record_lend.dart` — lifetime of lent buffers across isolates.
- Both run in `ci_generator.yml`; all gates were rehearsed on Linux with GCC.

## The rest of the bridge: the project's own benchmark

Scalars, strings, structs, maps, record lists, async and streams are covered by
`benchmark/tool/bench.sh` (the real app, macOS, profile mode). It was run four
times each on 0.8.8 and on this branch, alternating which went first. Every case
overlaps between the two; the regression gate passes on the branch.

| Case | 0.8.8 (4 runs) | Branch (4 runs) |
|---|---|---|
| `nitro_string_roundtrip` | 0.15–0.16 µs | 0.15–0.17 µs |
| `nitro_struct_roundtrip` | 0.09–0.10 µs | 0.09–0.10 µs |
| `nitro_cpp_map` | 1.39–1.79 µs | 1.69–1.77 µs |
| `nitro_cpp_record_list` | 1.02–1.34 µs | 1.13–1.35 µs |

Two cases looked slower on the branch whenever it ran second
(`nitro_buffer_pinned`, `nitro_native_async_scalar_xthread_spin`). So did
`raw_ffi_buffer`, which contains no Nitro code, and all three evened out when the
order was reversed: it is the second slot, not the build.

Variants are in the Dart and C++ table above; in Kotlin and Swift they share the
record reader and writer and are covered by the type-coverage suite.

## What is left, and why

Measured, not fixed:

| Path | Cost | Why it stays |
|---|---|---|
| Dart `String` encode | 0.7 ns per ASCII char, 3.4 per 2-byte char | The VM has no bulk string-to-bytes. A `codeUnitAt` loop, four and eight units per store, `utf8.encode` and `setRange(codeUnits)` were all measured; eight per store is the fastest. |
| Dart `List<int>` / `List<double>` / `List<bool>` decode | 1.3–2.6 ns per element | Allocating the growable list is about 1 ns per element on its own, and each double is boxed. A typed list is 0.1–0.4 ns per element and is lent without a copy; returning one in place of a `List<T>` would make the list fixed-length. |
| C++ `List<bool>` decode | 2.1 ns per element | `std::vector<bool>` is bit-packed and has no bulk write; one bounds check for the whole list was measured at 5% and left out. |
| Kotlin `List<int>` / `List<double>` encode on ART | 3 ns per element | The elements of a `List<Long>` are boxed; reading each one is the cost. |
| Kotlin string decode on ART | 1.6–1.8 ns per char for long strings | ART's `String` constructors; ASCII already takes the faster Latin-1 one. |
| Kotlin field decode on ART | about 30 ns per scalar field, 21 ns per `Record{double, double}` in a list | Mostly allocating the objects (8 ns per two-double record on its own) and, for strings, ART's `String` constructor. Variants still read through `ByteBuffer`: the same cursor was tried for the variant reader and measured no gain (a `{int, double, String}` case: 155 ns before, 165 ns after), because setting the cursor up costs what three or four reads save. A struct inside a record or variant also reads through `ByteBuffer`; structs otherwise cross as C structs. |
| Dart map decode | 60 ns per `int` entry, 95 ns per `String` entry | Inserting into the map and building the key string. The decoder now reads the payload in place (it copied it first) and decodes record and variant values in place (it allocated, copied and freed per entry); for plain values that is 2–4%. |
| `List<String>`, every language | 5–62 ns per string | One allocation and one decode per string. |
| Dart → native typed data in a record | three passes over the bytes | `writeBlob`, `toNative`, and the native side's own copy. `@zeroCopy` parameters avoid all three. |

## Where it was run

The regenerated `nitro_type_coverage` suite (775 tests, with every typed-data
field lent) passes on macOS, on an iPhone 12 and on the Android emulator;
`nitro_http`'s real-socket suite passes on macOS. All gates pass on macOS and on
Linux (GCC, in a container).

The generated desktop bridge and the record codecs also compile and link for a
Windows target with MinGW (GCC 16); they were not run there, and MSVC was not
tried.

Not timed: phones (the iPhone run is a correctness run) and Windows. Not run at
all: Windows, and a physical Android device. Kotlin timings are from an emulator
without AOT compilation.
