# Nitro benchmark results — platforms, modes, and numbers

All timings are **medians in microseconds (µs)** per call; buffer rows are MB/s.
Every run verifies that all bridge tiers produce **identical results** for both
workloads before timing anything — a mismatch aborts the run, so each column
provably compares the same work with only the bridge differing.

Generated by `tool/bench.sh`; raw reports archived under `results/<platform>-<mode>.json`
(each carries the `device` it ran on).

> **Latest run — nitro 0.5.17 (Aug 2026).** macOS `MacBookPro18,3` (M1 Pro) ·
> iPhone 12 (`iPhone13,2`, real device) · OnePlus CPH2447 (Snapdragon 8 Gen 2,
> Android 16, real device). All three verified `allTiersAgree = true`.
> macOS/iOS are **profile** (iOS profile ≡ release, §5; macOS release blocked
> by a Flutter SDK bug, §1 ¹); Android is a **release** pass on real hardware
> (true `-O2` native). An Android emulator profile↔release delta is in §2.

## 2. Device results — nitro 0.5.17 run

Columns: **macOS M1 Pro (profile)** · **iPhone 12 (profile, real device)** ·
**OnePlus CPH2447 (release, real device)** — Snapdragon 8 Gen 2, Android 16.
Compare tiers *within* a column, not across (different silicon). All three
verified `allTiersAgree = true`. Two of three columns are real hardware; the
Android emulator profile↔release check is in the delta table below.

### Sync call latency (µs/call, lower is better)

| Case | macOS M1 Pro | iPhone 12 | OnePlus (rel) |
|---|---|---|---|
| Raw FFI (leaf) — floor | 0.011 | 0.009 | 0.019 |
| Nitro C++ (leaf) | 0.255 | 0.221 | 0.439 |
| Nitro C++ (checked) | 0.256 | 0.223 | 0.457 |
| Nitro platform (Swift / Kotlin) | 0.263 | 0.233 | 0.732 |
| Nitro String round-trip | 0.515 | 0.522 | 0.992 |
| Nitro zero-copy struct | 0.403 | 0.363 | 0.820 |
| MethodChannel | 27.0 | 22.7 | 60.8 ³ |

**MethodChannel ÷ Nitro C++ (checked): 105× (macOS) · 102× (iOS) · 133× (OnePlus).**

³ The MethodChannel row is the noisiest measurement in the suite; Nitro rows are
stable to ~1%. Android's channel cost (JNI + platform-thread hop) is genuinely the
heaviest, which is why the Android speedup is the largest.

### Collection & async (µs/call)

| Case | macOS M1 Pro | iPhone 12 | OnePlus (rel) |
|---|---|---|---|
| `Map<String,int>` encode | 3.53 | 3.29 | 5.98 |
| `List<@HybridRecord>` ×16 | 1.75 | 1.59 | 3.90 |
| `@nitroAsync` record | 27.8 | 31.1 | 107.6 |
| `@nitroNativeAsync` record | 28.2 | 30.8 | 77.3 |

Async pays one `Dart_PostCObject` / isolate hop, so its latency sits in
MethodChannel territory — the async win is running work off the platform thread,
not raw latency. The **sync** path is where Nitro is ~100–133× ahead.

### Workload A — FNV-1a hash (1 KiB × 16 rounds, payload crosses the bridge)

ALU-chain bound; each call also marshals a 1 KiB buffer.

| Tier | macOS M1 Pro | iPhone 12 | OnePlus (rel) |
|---|---|---|---|
| Raw FFI → C | 21.0 | 22.0 | 24.3 |
| Nitro → C++ | 21.7 | 22.3 | 26.6 |
| Nitro → Swift / Kotlin | 21.5 | 22.4 | 34.8 |
| MethodChannel | 51.1 | 45.2 | 100.7 |

### Workload B — Sieve of Eratosthenes (limit 4096, int-only signature)

Allocation + strided writes + branches; ~zero marshalling, so this isolates
**pure implementation-language compute**.

| Tier | macOS M1 Pro | iPhone 12 | OnePlus (rel) |
|---|---|---|---|
| Pure Dart (no bridge) | 14.7 | 14.3 | 19.9 |
| Raw FFI → C | 8.66 | 8.83 | 10.2 |
| Nitro → C++ | 8.68 | 9.16 | 10.8 |
| Nitro → Swift / Kotlin | 6.99 | 8.72 | 25.7 |
| MethodChannel | 36.2 | 30.8 | 83.3 |

Reading it: Dart AOT is ~1.6–1.7× off C on identical compute. **Swift matches or
beats C** (bounds-check-eliminated `[Bool]` vs `calloc`/`free` per call), while
**Kotlin/JNI is ~2.4× slower than C++** on the real device — the honest,
optimized picture.

### Buffer throughput (16 MiB, MB/s, higher is better)

| Case | macOS M1 Pro | iPhone 12 | OnePlus (rel) |
|---|---|---|---|
| MethodChannel copy | 3,626 | 4,255 | 772 |
| Raw FFI (manual copy) | 30,159 | 12,699 | 11,746 |
| Nitro pinned buffer | 28,689 | 12,653 | 11,330 |

Nitro's pinned buffer is at parity with hand-written FFI on every platform, and
3–15× the channel's bandwidth (the OnePlus channel copy is the narrowest at
772 MB/s vs Nitro's 11.3 GB/s).

## 4. The Android `-O0` finding (fixed)

**Symptom:** on Android, Kotlin/JNI appeared to beat NDK-compiled C++ by ~3×
on both algorithms — on emulator *and* real hardware.

**Root cause:** the Android Gradle Plugin builds a plugin's
`externalNativeBuild` using the **DEBUG CMake config** for Flutter's `profile`
variant unless the plugin declares a matching `buildType`. The entire native
library shipped at `-O0`. Confirmed at the binary level:

| Exported symbol | profile `.so` | release `.so` |
|---|---|---|
| `fnv1a_hash` | 52 bytes (call shim) | 100 bytes (inlined) |
| `sieve_primes` | 36 bytes | 336 bytes |

**Fix** (`android/build.gradle`, and nitrogen's scaffold template so new plugins
inherit it):

```gradle
buildTypes {
    profile { initWith release }
}
```

**Impact** — sieve on OnePlus CPH2447:

| Tier | profile (broken) | profile (fixed) | release |
|---|---|---|---|
| Raw FFI → C | 40.6 | 10.7 | 7.6 |
| Nitro → C++ | 41.0 | 12.1 | 8.3 |
| Nitro → Kotlin (JNI) | 29.7 | 31.5 | 18.7 |

Raw FFI got **3.8× faster** from the fix alone, and C++ then beats Kotlin as
expected. Kotlin barely moved across all three columns — the signature
confirming the diagnosis, since ART was AOT-compiling it all along.

## 5. Why iOS needs no separate release run

Xcode's **Profile configuration inherits Release** in Flutter's iOS template:

- `VALIDATE_PRODUCT = YES` in Profile (absent in Debug) — a release-grade marker
- Profile's `App.framework/App` is a genuine AOT snapshot: **7.8 MB**, versus
  7.7 MB for release (a debug/JIT build's is a fraction of that)

So iOS `--profile` already measures release-grade native code plus AOT Dart.
Unlike Android, there was no bug to fix.

## 6. Reproducing

```sh
tool/bench.sh -d <device-id> --mode quick            # profile (default) + regression gate
tool/bench.sh -d <device-id> --mode quick --release  # release measurement, no gate
tool/bench.sh -d macos --mode full --update-baseline # re-record a baseline
```

`--release` cannot use `flutter test`/`drive`, so the app runs the identical
harness headlessly (`--dart-define=BENCH_AUTORUN=<mode>`), prints `BENCH|` lines
plus the report JSON in logcat-safe chunks, and exits; `bench.sh` reassembles
and archives it.

**Harness-path equivalence** (same phone, same mode): compute-bound cases
reproduce within ~1% between the autorun and `flutter drive` paths (raw FFI FNV
22.34 → 22.27 µs; raw FFI sieve 8.98 → 8.93; pure-Dart sieve 14.21 → 14.22).
Bridge-dispatch cases are *cleaner* on the autorun path (MethodChannel
28.0 → 21.6 µs, `@nitroAsync` 53.7 → 30.1) because no driver extension competes
for the platform thread.

### A note on units

All latency numbers are **microseconds**, verified four ways: the harness
computes `Stopwatch.elapsedMicroseconds / iterations`; total measured time
summed across cases is 0.8 s (a milliseconds reading would imply 13 minutes,
impossible inside the observed 141 s wall clock including the build); 0.013 µs
for a leaf FFI call is ~50 CPU cycles on an M4; and 16 MiB ÷ 525 µs = 31.9 GB/s
is real memcpy bandwidth (a ms reading would give 31.9 MB/s).
